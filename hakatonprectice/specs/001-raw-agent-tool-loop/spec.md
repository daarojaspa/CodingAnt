# Feature Specification: Raw Agent + 3 Basic Tools (P1)

**Feature Branch**: `001-raw-agent-tool-loop`

**Created**: 2026-08-07

**Status**: Draft

**Input**: User description: "p1: raw agent + 3 basic tools — a multiturn console loop where the agent evaluates whether it needs a tool and calls it. Three tools: read_file, write_file, run_bash. Explicit stop conditions: bounded retries with geometric backoff, a 6000-token-per-answer budget, and a max of 10 loop iterations without producing an answer. The agent must fail gracefully; the tool-calling loop inside the main loop must be robust."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Agent creates a working program on request (Priority: P1)

A developer starts the agent in a console session inside a project folder and asks it, in plain language, to build a small program. The agent decides on its own that it needs to write a file, writes it, and reports back what it created. The developer can then continue the conversation in the same session, referring to what just happened.

**Why this priority**: This is the minimum proof that the loop closes — the model's stated intent turns into a real change on disk and the result comes back into the conversation. Without it, nothing else in the feature has value.

**Independent Test**: Start a session, ask for "a console program that asks for a number `a` and a base `b` and prints log base b of a". Confirm `log.py` exists afterward and runs correctly when executed by hand. Delivers value on its own: the agent can produce new code.

**Acceptance Scenarios**:

1. **Given** an empty project folder and a running session, **When** the user asks for a console program computing log base b of a, **Then** the agent writes `log.py` into the project folder and states in the conversation that it did so.
2. **Given** the agent has just written `log.py`, **When** the user runs it manually with a=8, b=2, **Then** it prompts for both values and prints 3 (within normal floating-point tolerance).
3. **Given** the agent has completed a request, **When** the user sends a follow-up message referring to "that file", **Then** the agent responds using the earlier turns of the same session as context.

---

### User Story 2 - Agent reads, modifies, and verifies existing code (Priority: P1)

The developer asks the agent to extend a file that already exists. The agent reads the current contents, rewrites the file with the new capability, runs it to check the change works, and reports the outcome — chaining three tools inside a single request without the developer stepping in.

**Why this priority**: Multi-tool chaining with verification is the actual P1 deliverable. Writing a file blindly is not a coding agent; reading before writing and running after writing is.

**Independent Test**: With an existing `log.py`, ask the agent to also compute the exponential of `a` raised to `b`. Confirm the agent read the file, rewrote it, executed it, and stated whether the new behaviour worked.

**Acceptance Scenarios**:

1. **Given** `log.py` exists in the project folder, **When** the user asks to add exponentiation of a to the power b, **Then** the agent reads the existing file before rewriting it.
2. **Given** the rewrite has been made, **When** the agent finishes the request, **Then** it has executed the file at least once and reported the observed output as evidence the new feature works.
3. **Given** the executed file raises an error, **When** the agent sees the failure output, **Then** it either corrects the file and re-runs it, or stops and states plainly what failed — it does not claim success.
4. **Given** the user asks the agent to read a file by name with no path, **When** the file sits in the folder the agent was started from, **Then** the agent locates and loads it without the user supplying an absolute path.

---

### User Story 3 - Session stays inside its sandbox (Priority: P1)

The developer trusts the agent to run shell commands only because it cannot reach outside the folder it was started in. Any request — from the user or self-generated by the agent — that would read, write, or execute against a path outside the project root is refused, with the refusal stated in the conversation.

**Why this priority**: Constitution VI and VII are non-negotiable. An agent with unrestricted `run_bash` cannot be run at all, so this gates the whole feature rather than following it.

**Independent Test**: Ask the agent to read `~/.ssh/id_rsa`, to write into the parent directory, and to run a command that touches a home-directory path. Confirm all three are refused and the filesystem outside the project root is untouched.

**Acceptance Scenarios**:

1. **Given** a running session, **When** the agent attempts to read a path resolving outside the project root, **Then** the read is refused and the refusal reason is returned to the agent as the observation.
2. **Given** a running session, **When** the agent attempts to write to a path resolving outside the project root, **Then** the write is refused and no file is created anywhere.
3. **Given** a running session, **When** a shell command would act on a location outside the project root, **Then** the command is refused rather than executed.
4. **Given** a path that stays inside the project root only by way of symlinks or `..` segments, **When** it is resolved, **Then** resolution happens before the check so the boundary cannot be escaped.
5. **Given** a request that falls under the constitution's absolute prohibitions or consent gates, **When** the agent evaluates it, **Then** it refuses and states which rule applies.

---

### User Story 4 - Failures are bounded and visible (Priority: P2)

When a tool throws or the model API call fails, the agent retries a bounded number of times with growing waits, and if it still cannot proceed it stops and tells the developer exactly how many attempts it made and how long it waited between each. The developer never watches it spin.

**Why this priority**: The stated purpose of this phase is graceful failure. It is P2 only because the happy paths must exist before failure behaviour can be observed — but the phase is not done without it.

**Independent Test**: Deliberately break a tool (or point the session at an unreachable API endpoint), issue a request, and confirm the session ends within the retry cap with a message naming the attempt count and the wait between each.

**Acceptance Scenarios**:

1. **Given** a tool raises an error mid-run, **When** the agent receives the failure, **Then** it retries up to the configured cap with each wait longer than the last by a fixed ratio.
2. **Given** the retry cap is exhausted, **When** the agent gives up, **Then** it halts cleanly and its final message names the number of retries and the wait used before each one.
3. **Given** the model API call itself fails, **When** the failure is transient, **Then** the same bounded retry-with-backoff behaviour applies as for tool failures.
4. **Given** a request that the agent cannot satisfy, **When** it has taken 10 loop iterations without producing an answer to the user, **Then** it stops and states that it hit the iteration cap without finishing.
5. **Given** any session, **When** it ends for any reason, **Then** it ends with a stated reason rather than silently or by spinning.

---

### User Story 5 - Responses stay within budget (Priority: P3)

The developer is paying per token and wants each agent reply bounded, so a runaway generation cannot burn the budget in one turn.

**Why this priority**: Cost control matters but does not block the loop from working; it can be layered on once the loop and its failure handling are proven.

**Independent Test**: Issue a request that invites a very long answer and confirm no single agent response exceeds the per-answer token ceiling, and that a truncated answer is reported as truncated.

**Acceptance Scenarios**:

1. **Given** a running session, **When** the agent produces any single response, **Then** that response is capped at 6000 tokens.
2. **Given** a response hits the cap, **When** it is shown to the user, **Then** the session states that the answer was cut short by the token budget rather than presenting it as complete.

---

### Edge Cases

- The user asks to read a file that does not exist → the failure is returned to the agent as an observation it can act on, not as a crash of the session.
- The user asks to read a very large or binary file → the session handles it without corrupting the conversation or exhausting the context.
- A shell command hangs or never returns → it is cut off by a time limit and the timeout is reported as the observation.
- A shell command exits non-zero → both the exit status and the error output reach the agent so it can react.
- A write targets a directory that does not yet exist inside the project root → the intended behaviour is stated rather than left to chance.
- A write targets an existing file → the prior contents are replaced, and this is visible in what the agent reports.
- The agent requests a tool that does not exist, or supplies malformed arguments → the mismatch is returned as a recoverable observation, not a crash.
- The user interrupts the session mid-run → it exits cleanly with a stated reason.
- The agent asks for several tools in one turn → all are handled and their results returned before the next model turn.
- Retry backoff and the iteration cap interact → hitting either limit ends the run with one clear stated reason, not two competing ones.

## Requirements *(mandatory)*

### Functional Requirements

**Conversation loop**

- **FR-001**: The system MUST hold a multi-turn conversation in the console, where the user types a message and the agent replies, repeating until the user ends the session.
- **FR-002**: The system MUST carry the full prior turns of the session into each new agent turn, so replies depend on the whole history.
- **FR-003**: On each agent turn, the system MUST let the agent decide whether a tool is needed, and if so, execute the requested tool before the agent's next turn.
- **FR-004**: The system MUST return every tool result — success or failure — into the conversation as the observation for the agent's next turn.
- **FR-005**: The system MUST support several tool requests arising from a single agent turn, returning every result before continuing.
- **FR-006**: The system MUST end each request either with an answer to the user or with an explicitly stated stop reason.

**Tools**

- **FR-007**: The system MUST provide a `read_file` tool that loads a named file's contents into the conversation, accepting either an explicit path or a name resolved relative to the folder the agent was started in.
- **FR-008**: The system MUST provide a `write_file` tool that writes given content to a named location chosen by the agent.
- **FR-009**: The system MUST provide a `run_bash` tool that executes arbitrary shell commands and returns their standard output, standard error, and exit status.
- **FR-010**: `run_bash` MUST apply a wall-clock time limit per command and report a timeout as an ordinary observation.
- **FR-011**: Each tool MUST report failure as a described observation the agent can act on, never as an unhandled crash of the session.

**Boundary and safety**

- **FR-012**: The system MUST refuse any read, write, or command execution whose target resolves outside the project root — the folder the agent was started in.
- **FR-013**: The system MUST resolve paths fully — following `..` segments and symlinks — before applying the boundary check.
- **FR-014**: The system MUST state a refusal in the conversation whenever an action is blocked, naming the reason.
- **FR-015**: The system MUST refuse actions falling under the constitution's absolute prohibitions (VI) and MUST NOT perform consent-gated actions (VII) silently.

**Stop conditions**

- **FR-016**: The system MUST retry a failed tool call a bounded number of times, waiting longer before each successive attempt by a fixed geometric ratio.
- **FR-017**: The system MUST apply the same bounded, backing-off retry behaviour to failed model API calls.
- **FR-018**: When retries are exhausted, the system MUST stop and report the number of retries attempted and the wait used before each.
- **FR-019**: The system MUST cap any single agent response at 6000 tokens.
- **FR-020**: The system MUST state when a response was cut short by the token cap.
- **FR-021**: The system MUST stop a request after 10 loop iterations without an answer to the user, and say so.
- **FR-022**: The system MUST never loop unbounded — every path through the loop reaches an answer, a cap, or a stated failure.

**Out of scope for this feature**

- Memory persisting between sessions.
- Orchestrating multiple models or sub-agents.
- Any file or command access outside the folder the agent was started in.

### Key Entities

- **Session**: One console conversation from start to exit. Holds the ordered turns and the counters that enforce the caps. Does not survive process exit.
- **Turn**: One entry in the conversation — a user message, an agent message, a tool request, or a tool observation.
- **Tool**: A named capability the agent may invoke, with a described purpose and expected arguments. Three exist: `read_file`, `write_file`, `run_bash`.
- **Tool Result**: The observation returned from one tool invocation — its output, or a description of how it failed or why it was refused.
- **Project Root**: The folder the agent was started in. The outer boundary of every filesystem and command action.
- **Stop Reason**: The stated cause a request ended — answered, retries exhausted, iteration cap reached, token cap reached, refused, or user exit.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Told to create a console program computing log base b of a, the agent produces a working `log.py` with no user intervention beyond the initial request.
- **SC-002**: Told to extend `log.py` with exponentiation, the agent reads, rewrites, and runs the file within a single request, and reports the observed result — chaining all three tools unattended.
- **SC-003**: Across 10 runs of the two acceptance tasks above, at least 8 complete unattended.
- **SC-004**: 100% of attempts to act outside the project root are refused, verified against a set of at least 5 escape attempts including relative paths and symlinks.
- **SC-005**: With a tool deliberately broken, 100% of runs end within the retry cap with a stated reason — none spin or hang.
- **SC-006**: Every terminated run reports a stop reason; runs that exhausted retries also report the attempt count and each wait interval.
- **SC-007**: No request exceeds 10 loop iterations without an answer, and no single response exceeds 6000 tokens, across all test runs.
- **SC-008**: An unattended acceptance task completes in under 2 minutes of wall-clock time.

## Assumptions

- The developer runs the agent from a terminal inside the project folder they want it to act on; that folder is the project root and the boundary.
- A single developer uses the agent interactively. No concurrent sessions share state.
- The 6000-token cap applies to each individual agent response, not to a cumulative session total; no session-wide budget is in scope for this phase.
- The retry cap and the backoff ratio are fixed configuration values chosen during planning; the requirement is that they are bounded, geometric, and reported — not that they take particular values.
- The 10-iteration cap counts loop iterations within one user request, and resets when the agent returns an answer and the user speaks again.
- Retries apply to failures that could plausibly succeed on a second attempt. A refusal on safety grounds is a final answer and is never retried.
- Model access is via the official Anthropic API SDK with an API key supplied through a `.env` file, per the constitution's stack constraints.
- The console is the only interface. No graphical or web front end is in scope.
- Shell commands run with the developer's own privileges; the agent never escalates.
